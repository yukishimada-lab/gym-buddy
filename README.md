# 💪 gym-buddy

筋トレを記録するための個人向け Web アプリです。ジムでスマホから、その日のワークアウト(種目・重量・回数・セット数)をサクッと記録できます。

## 主な機能(Phase 1)

- **Google / GitHub アカウントでログイン**(Supabase Auth)
- **ワークアウト記録**: 日付ごとに種目・重量(kg)・回数(レップ)・セット数を記録/編集/削除
- **種目マスタ**: よく使う種目(ベンチプレス、スクワット等)を登録・管理。初回サインアップ時に代表的な種目が自動登録されます
- **ルーティン管理**: 「胸の日」「脚の日」のような種目の組み合わせを保存し、記録ページからワンタップでその日の記録に展開
- **履歴一覧**: 過去の記録を日付ごとに一覧表示

## 主な機能(Phase 2: 食事管理と PFC 計算)

- **食品マスタ**: 白米・鶏むね肉・卵・納豆・プロテインなど定番食品約 30 品目の PFC・カロリー(100g あたり)を初期データとして収録
- **食事記録**: 日付 × タイミング(朝食/昼食/夕食/間食)ごとに、食品+グラム数を複数品目記録/編集/削除。食品マスタから検索して選ぶと、グラム数から PFC・カロリーを自動計算
- **写真からの自動推定**: 食事の写真をアップロードすると、Gemini Vision API が品目とおおよそのグラム数・PFC を推定してフォームに自動入力(内容は記録前に修正できます)。写真は Supabase Storage に保存されます
- **外食メニューの栄養情報検索**: 店名+メニュー名を入力すると、Gemini API の Google 検索グラウンディングで公式の栄養成分情報を検索してフォームに自動入力(見つからない場合は手動入力)
- **日別の PFC・カロリー合計**: その日の食事一覧と、カロリー・タンパク質・脂質・炭水化物の合計を表示

## 主な機能(Phase 3: 体重・InBody データの記録と目標サポート)

- **体重記録**: 日付ごとに体重(kg)とメモを記録/編集/削除。1 日 1 件を基本とし、同じ日付で記録すると上書きされます
- **InBody データ記録**: 体脂肪率(%)・骨格筋量(kg)・体脂肪量(kg)・基礎代謝量(kcal)・体水分量(L)を測定日ごとに記録。項目はすべて任意なので、測定できた項目だけ入力すれば OK です
- **推移グラフ**: 体重・体脂肪率・骨格筋量の時系列グラフ(Recharts)。**1ヶ月 / 3ヶ月 / 全期間**で期間を切り替えできます。単位もスケールも違う 3 指標を 1 つのグラフに重ねる(2 軸グラフ)のではなく、指標ごとにグラフを分けて誤読を防いでいます
- **目標設定**: 目標体重・目標体脂肪率・目標達成希望日・モード(増量/減量/維持)を設定
- **目標サポート分析**:
  - 現在地から目標までの差分と、達成に必要な **1 日あたりのカロリー収支**(体重 1kg = 7,200kcal 換算)の目安
  - Phase 2 の食事記録と組み合わせた、**直近 14 日の平均摂取カロリー・平均タンパク質**が目標に対して足りているか/超過しているかの判定
  - 直近 28 日の体重記録から求めた**週あたりの増減ペース**と、そのペースが続いた場合の**目標達成予測日**
  - 上記の数値(体重推移・目標・直近の食事傾向・トレーニング頻度)を Gemini API に渡して生成する、**日本語の AI アドバイス**(サーバーサイドで実行)

## 主な機能(Phase 4: セット単位の記録・並べ替え・カレンダー)

- **セットごとの重量・回数**: 「1セット目 80kg×10回 / 2セット目 80kg×8回 / 3セット目 70kg×8回」のように、セット単位で重量と回数を記録できます。セットの追加・削除も自由で、追加したセットには直前のセットの数値が引き継がれます
- **前回記録との比較**: 同じ種目の前回の記録と比べて、**最大重量**と**総ボリューム(重量 × 回数の合計)**が伸びていれば青、下がっていれば赤で表示します。色だけに頼らないよう ↑ ↓ の矢印と差分の数値(「前回比 +2.5kg」)も併記しています。前回の記録がない種目には色を付けません
- **ドラッグ&ドロップの並べ替え**: 記録の中の種目も、ルーティンの中の種目も、⠿ ハンドルを長押ししてドラッグすると順番を入れ替えられます(スマホのタッチ操作に対応。キーボード操作でも並べ替えできます)
- **ルーティンの数値の編集**: ルーティンに登録した種目の目標セット数・重量・回数を、あとから編集できます
- **からだの記録を 1 画面に統合**: 体重記録と InBody 記録を 1 つのテーブル(`body_logs`)にまとめました。日付ごとに 1 件で、体重は必須・InBody の各項目は任意。InBody を測れない日は体重だけ記録できます
- **カレンダー**: 月表示でトレーニングした日(青)と食事記録がある日(オレンジ)が一目で分かります。色だけでなくマークの形(塗りつぶし丸 / 輪郭だけの丸)でも区別し、凡例も添えています。日付をタップするとその日の内容が表示され、記録ページ・食事ページへ移動できます

## 主な機能(Phase 5: 部位ごとの表示・1 日サマリーの画像共有)

- **種目の部位(部位マスタ)**: 種目を「胸 / 背中 / 肩 / 腕 / 脚 / 体幹 / 有酸素 / その他」の 8 区分で管理します。既存の種目には種目名から自動で部位を割り当て済みで(`supabase/migrations/` のマイグレーションで自動適用)、種目マスタの「編集」からいつでも変更できます
- **カレンダーの日別詳細を部位ごとに表示**: その日にやった種目を部位ごとのセクション(「胸(3種目)」など)に分けて表示します。並び順は 胸 → 背中 → 肩 → 腕 → 脚 → 体幹 → 有酸素 → その他 で固定です
- **数値にラベルを付けた要約**: 「3セット · 最大80kg · 総ボリューム1,920kg」のように、それぞれの数値が何を指すのかが分かる表記にしました。重量を入力していない記録(自重種目やルーティンを展開しただけの記録)は「0kg」ではなく「3セット · 重量なし · 計30回」と表示します
- **1 日のサマリーを画像で共有**: カレンダーの日別詳細の「この日を画像で共有」から、その日の内容(トレーニング / 食事の PFC・カロリー / 体重・InBody)を 1 枚の縦長 PNG として書き出せます。画像はブラウザ内だけで生成し(サーバーには送りません)、**その日に記録がある項目だけ**を載せます。共有は Web Share API に対応した端末では共有シート、非対応の端末では画像を表示して長押し保存 / ダウンロードできます
- **ルーティン展開時の重量の引き継ぎ**: ルーティンに目標重量を設定していない種目は、その種目の**前回の記録**の重量・回数を初期値として展開するようになりました(以前は 0kg のセットが作られていました)。また、すでにその日に記録がある種目を含むルーティンを展開しようとすると確認が入ります


## 主な機能(Phase 6: 種目の一括削除)

- **選択モードで種目をまとめて削除**: 記録タブの「選択して削除」を押すと各種目にチェックボックスが出ます。カードのどこをタップしても選べる大きめのタップ領域にしてあり、「すべて選択 / すべて解除」のトグルと、選んだ件数を出す「3件を削除」ボタンで一気に消せます
- **その日の種目をすべて削除**: 間違ったルーティンを展開してしまったときのために、「ルーティンから一括追加」のすぐ下に「間違えて展開した? この日の種目をすべて削除(N件)」の導線を置いています
- **必ず件数を出す確認ダイアログ**: 削除の前に「3件の種目を削除します。よろしいですか?」と件数・種目名を出します(1 件だけの削除も同じ確認を通ります)
- **数秒間の「元に戻す」**: 削除後 8 秒間だけ画面下に「元に戻す」が出ます。押すと削除前とまったく同じ内容(セットの重量・回数・並び順)で復元されます
- **セットの記録も必ず一緒に削除**: `workout_sets` → `workout_logs` の順にアプリ側から明示的に削除するので、親を消してセットだけが残る(孤児レコード)ことがありません

## セットアップ手順

初めての方でも順番にやれば動くように書いています。全体の流れは次の 4 ステップです。

1. Supabase プロジェクトを作る
2. データベース(テーブル)を作る
3. ログイン方法(GitHub / Google)を設定する
4. アプリを起動する(ローカル or Vercel)

### 1. Supabase プロジェクトの作成

1. [https://supabase.com](https://supabase.com) を開き、右上の **Sign In** をクリックします。
2. **Continue with GitHub** を選ぶと、GitHub アカウントでそのままサインアップ/ログインできます(GitHub アカウントがない場合は先に [github.com](https://github.com) で作成してください)。
3. ログイン後、**New Project** をクリックします。
4. 以下を入力してプロジェクトを作成します。
   - **Name**: `gym-buddy` など好きな名前
   - **Database Password**: 自動生成でOK(メモしておくと安心)
   - **Region**: `Northeast Asia (Tokyo)` を選ぶと日本から速いです
5. 1〜2 分でプロジェクトが作成されます。

### 2. データベースのセットアップ(マイグレーションの適用)

テーブルの定義は [`supabase/migrations/`](./supabase/migrations) にマイグレーションファイルとしてまとまっています。**既存の本番プロジェクトでは、GitHub Actions が main へのプッシュ時に自動で適用します**(→ [DB マイグレーションの運用](#db-マイグレーションの運用))。

新しく作った Supabase プロジェクトに一括で流す場合は、次のどちらかで適用してください。

**方法 A: Supabase CLI(推奨)**

```bash
npx supabase link --project-ref <プロジェクトの ref>
npx supabase db push
```

**方法 B: SQL Editor に貼り付け**

Supabase ダッシュボードの **SQL Editor** で、`supabase/migrations/` のファイルを**ファイル名の順番どおりに**(`20260901035412_...` → `20260901130705_...` → …)1 つずつ貼り付けて **Run** します。

これでテーブル(種目・記録・ルーティン・食事・からだの記録)と、ユーザーが自分のデータにしかアクセスできないようにするセキュリティ設定(Row Level Security)が作成されます。新規ユーザーには代表的な種目(ベンチプレス、スクワット等)が自動で登録されます。

### 3. GitHub OAuth(GitHub ログイン)の設定

アプリに「GitHub でログイン」するための設定です。**GitHub 側**と **Supabase 側**の 2 箇所を設定します。

> 「Google でログイン」も使えるようにするには、あわせて [Google ログインの設定手順](#google-ログインの設定手順) を行ってください(こちらは Google Cloud Console と Supabase の設定だけで、コードの変更は不要です)。

#### 3-1. GitHub で OAuth App を作成

1. GitHub にログインし、[https://github.com/settings/developers](https://github.com/settings/developers) を開きます。
2. **OAuth Apps** → **New OAuth App** をクリックします。
3. 以下を入力します。
   - **Application name**: `gym-buddy` など好きな名前
   - **Homepage URL**: `http://localhost:3000`(あとで Vercel の URL に変えてもOK)
   - **Authorization callback URL**: ここが重要です。Supabase ダッシュボードの **Authentication → Sign In / Providers → GitHub** に表示されている **Callback URL** をコピーして貼り付けます。形式は次のようになります。
     ```
     https://<プロジェクトのref>.supabase.co/auth/v1/callback
     ```
4. **Register application** をクリックします。
5. 表示された **Client ID** をメモします。**Generate a new client secret** をクリックして **Client Secret** も作成し、メモします(この画面を閉じると二度と見られないので注意)。

#### 3-2. Supabase に GitHub プロバイダを設定

1. Supabase ダッシュボードの **Authentication → Sign In / Providers** を開きます。
2. **GitHub** を選び、**Enable Sign in with GitHub** をオンにします。
3. 先ほどメモした **Client ID** と **Client Secret** を貼り付けて **Save** します。

#### 3-3. リダイレクト URL の設定

1. Supabase ダッシュボードの **Authentication → URL Configuration** を開きます。
2. **Site URL** にアプリの URL を設定します。
   - ローカル開発なら: `http://localhost:3000`
   - Vercel にデプロイしたら: `https://あなたのアプリ.vercel.app`
3. **Redirect URLs** に以下を追加します(ローカルと本番の両方を登録しておくと便利です)。
   ```
   http://localhost:3000/auth/callback
   https://あなたのアプリ.vercel.app/auth/callback
   ```

### 4. ローカルでの起動

Node.js(v20 以上推奨)がインストールされている前提です。

```bash
# 1. リポジトリを取得
git clone https://github.com/yukishimada-lab/gym-buddy.git
cd gym-buddy

# 2. 依存パッケージをインストール
npm install

# 3. 環境変数ファイルを作成
cp .env.example .env.local
```

`.env.local` をエディタで開き、Supabase ダッシュボードの **Project Settings → API** に表示されている値を貼り付けます。

```
NEXT_PUBLIC_SUPABASE_URL=https://<プロジェクトのref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon public キー>
```

保存したら開発サーバーを起動します。

```bash
npm run dev
```

ブラウザで [http://localhost:3000](http://localhost:3000) を開き、「GitHub でログイン」または「Google でログイン」できれば成功です。

### 5. Vercel へのデプロイ

1. [https://vercel.com](https://vercel.com) を開き、**Continue with GitHub** でサインアップ/ログインします。
2. **Add New… → Project** をクリックし、`gym-buddy` リポジトリを **Import** します。
3. **Environment Variables** に以下の 2 つを追加します(値は `.env.local` と同じ)。
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
4. **Deploy** をクリックします。数分でデプロイが完了し、`https://〜.vercel.app` の URL が発行されます。
5. 発行された URL を使って、次の 2 箇所を更新します。
   - Supabase の **Authentication → URL Configuration**: Site URL と Redirect URLs(`https://〜.vercel.app/auth/callback`)
   - (必要なら)GitHub OAuth App の Homepage URL

これでスマホのブラウザからいつでも記録できるようになります。ホーム画面に追加しておくとアプリのように使えて便利です。

## Google ログインの設定手順

ログイン画面の「**Google でログイン**」ボタンを使えるようにするための設定です。作業するのは **Google Cloud Console** と **Supabase ダッシュボード** の 2 箇所だけで、アプリ側のコードや環境変数を足す必要はありません(所要時間の目安 15〜20 分)。

> 既存の「GitHub でログイン」はそのまま使えます。この設定をしなくても GitHub ログインは動きますが、**Google の設定をしないまま「Google でログイン」を押すとエラー画面になります**。知り合いに使ってもらう前に必ず設定してください。

### 手順 1: Supabase の「コールバック URL」を先にコピーしておく

1. [Supabase ダッシュボード](https://supabase.com/dashboard) で対象プロジェクトを開きます。
2. 左メニューの **Authentication** → **Sign In / Providers** を開きます。
3. プロバイダ一覧から **Google** をクリックして開きます。
4. 中に表示されている **Callback URL (for OAuth)** をコピーします。形式は次のとおりです。

   ```
   https://<プロジェクトのref>.supabase.co/auth/v1/callback
   ```

   ⚠️ `<プロジェクトのref>` の部分はプロジェクトごとに違います。**この画面に実際に表示されている値をそのままコピー**してください(手順 4 で貼り付けます)。この画面はこのあとも使うので、ブラウザのタブは開いたままにしておくと楽です。

### 手順 2: Google Cloud Console でプロジェクトを作る

1. [https://console.cloud.google.com/](https://console.cloud.google.com/) を開き、Google アカウントでログインします。
2. 画面**左上**のプロジェクト選択(「プロジェクトを選択」または既存のプロジェクト名が出ている部分)をクリックします。
3. ダイアログ右上の **新しいプロジェクト** をクリックします。
4. **プロジェクト名** に `gym-buddy` と入力して **作成** をクリックします(組織や場所は既定のままでOK)。
5. 作成が終わったら、左上のプロジェクト選択が `gym-buddy` になっていることを確認します。**ここが別のプロジェクトのままだと、以降の設定が違う場所に入ってしまいます。**

### 手順 3: OAuth 同意画面(ログイン時にユーザーに見える画面)を設定する

1. 左上のハンバーガーメニュー(≡)から **API とサービス** → **OAuth 同意画面** を開きます。
   - 新しい画面では **Google 認証プラットフォーム** という名前になっています。どちらでも中身は同じです。
2. 初回は「Google 認証プラットフォームへようこそ」と出るので **開始** をクリックします。
3. 順番に次を入力します。
   - **アプリ名**: `gym-buddy`(ログイン時にユーザーに表示される名前です)
   - **ユーザー サポートメール**: 自分のメールアドレスを選択
   - **対象**(古い画面では **User Type**): **外部** を選びます
     - 個人の Google アカウントでは「内部」は選べません。**「外部」で問題ありません。**
   - **連絡先情報**: 自分のメールアドレス
   - 利用規約のチェックを入れて **作成**
4. **データアクセス**(古い画面では **スコープ**)タブを開き、**スコープを追加または削除** をクリックします。
   一覧から次の 3 つだけにチェックを入れて、**更新** → **保存** します。

   | スコープ | 内容 |
   | --- | --- |
   | `.../auth/userinfo.email` | メールアドレスの取得 |
   | `.../auth/userinfo.profile` | 名前・アイコンなどの基本情報 |
   | `openid` | ログイン(本人確認)そのもの |

   > 💡 この 3 つはいずれも「機密スコープ / 制限付きスコープ」ではないため、**Google による審査(アプリの確認)は不要**です。Gmail の中身やカレンダーなどを要求すると審査が必要になりますが、このアプリでは一切要求しません。

5. **対象**(Audience)タブを開き、**公開ステータス**を確認します。ここがいちばん重要です。
   - **「テスト」のままだと、テストユーザーとして登録したメールアドレスの人しかログインできません。** 知り合いがログインしようとすると「アクセスをブロックしました: gym-buddy は Google の審査プロセスを完了していません」というエラーになります。
   - **アプリを公開**(**PUBLISH APP**)ボタンをクリックし、確認ダイアログで **確認** を押して、ステータスを **「本番環境」(In production)** にしてください。
   - 手順 4 のスコープだけであれば、公開してもそのまま(審査待ちなしで)使えます。

### 手順 4: OAuth クライアント ID(Client ID / Client Secret)を作る

1. 左メニューの **API とサービス** → **認証情報** を開きます(新しい画面では **Google 認証プラットフォーム** → **クライアント**)。
2. 上部の **+ 認証情報を作成** → **OAuth クライアント ID**(新しい画面では **クライアントを作成**)をクリックします。
3. **アプリケーションの種類**: **ウェブ アプリケーション** を選びます。
4. **名前**: `gym-buddy web` など、自分が分かる名前でOKです。
5. **承認済みのリダイレクト URI** の **+ URI を追加** をクリックし、**手順 1 でコピーした Supabase の Callback URL** をそのまま貼り付けます。

   ```
   https://<プロジェクトのref>.supabase.co/auth/v1/callback
   ```

   - ⚠️ ここに入れるのは **Supabase の URL** です。アプリ(Vercel)の URL `https://〜.vercel.app/auth/callback` ではありません。**実際の値は必ず Supabase の Authentication → Sign In / Providers → Google の画面に表示されているものをコピーしてください。**
   - **承認済みの JavaScript 生成元** は空のままで構いません。
6. **作成** をクリックすると、**クライアント ID** と **クライアント シークレット** が表示されるのでコピーしておきます。
   - この画面を閉じてしまっても、**クライアント**(認証情報)一覧から対象のクライアントを開けば再確認・再発行できます。

### 手順 5: Supabase に貼り付けて有効化する

1. 手順 1 で開いた Supabase の **Authentication → Sign In / Providers → Google** の画面に戻ります。
2. **Enable Sign in with Google** をオンにします。
3. 次の 2 つを貼り付けます。
   - **Client IDs**: 手順 4 の **クライアント ID**
   - **Client Secret (for OAuth)**: 手順 4 の **クライアント シークレット**
4. **Save** をクリックします。

補足として、**Authentication → URL Configuration** の **Redirect URLs** に、アプリの戻り先が登録されている必要があります(GitHub ログインの設定時に登録済みなら追加作業は不要です)。

```
http://localhost:3000/auth/callback
https://あなたのアプリ.vercel.app/auth/callback
```

### 手順 6: 動作確認

1. アプリを開きます(本番なら [https://gym-buddy-lac-one.vercel.app/](https://gym-buddy-lac-one.vercel.app/))。
2. 「**Google でログイン**」をクリックし、Google アカウントを選びます。
3. アプリのトップ(ワークアウト記録の画面)に戻れば成功です。
4. 下部ナビの「種目」タブを開き、代表的な種目(ベンチプレス、スクワット等)が並んでいれば、新規ユーザー用の初期データも入っています。
   - 万一 0 件だった場合は、その画面の「**代表的な種目をまとめて登録**」ボタンを押せば同じ内容が入ります。
   - 食品マスタ(食事タブで検索できる食品の一覧)は全ユーザー共通なので、初回から使えます。

うまくいかないときのチェックポイント:

| 症状 | 原因と対処 |
| --- | --- |
| `redirect_uri_mismatch`(リダイレクト URI が一致しません) | 手順 4-5 で登録した URI が、Supabase の Callback URL と 1 文字も違わず一致しているか確認してください(末尾のスラッシュや `http`/`https` の違いもNG) |
| 「アクセスをブロックしました: gym-buddy は Google の審査プロセスを完了していません」 | 手順 3-5 の**公開**をしていません。公開ステータスを「本番環境」にしてください |
| ログイン後に何度もログイン画面に戻される | Supabase の **Authentication → URL Configuration** の **Redirect URLs** に、使っている URL の `/auth/callback` が登録されているか確認してください |
| 「Unsupported provider: provider is not enabled」 | Supabase の Google プロバイダが有効(手順 5)になっていません |

### 同じメールアドレスで GitHub と Google の両方からログインしたときの挙動

Supabase Auth は、**プロバイダから「確認済み」として渡されたメールアドレスが既存ユーザーと同じ場合、自動的に同じユーザー(同じ user id)に結び付けます**(Identity Linking の自動リンク)。GitHub も Google も確認済みのメールアドレスを返すため、通常は次のようになります。

- **メールアドレスが同じ** → **同じアカウント**になります。GitHub で入っても Google で入っても同じ記録が見え、データが分断されることはありません。
- **メールアドレスが違う**(例: GitHub は会社のメール、Google はプライベートのメール)→ **別アカウント**として扱われ、記録も別々になります。これは仕様どおりの動作です。

**確認方法**: Supabase ダッシュボード → **Authentication** → **Users** を開きます。対象のユーザー行をクリックすると **Identities** に `github` と `google` の両方が並んでいれば、1 つのアカウントに統合されています。ユーザーが 2 行に分かれている場合は、メールアドレスが違っています。

注意点:

- GitHub 側でメールアドレスを非公開に設定していると、GitHub から渡されるアドレスが `〜@users.noreply.github.com` になり、Google のメールアドレスと一致しません。その場合は別アカウントになります。
- **一度別々にできてしまった記録を、後からアプリ上で 1 つに統合する機能はありません。** 普段使うログイン方法は 1 つに決めておくのが安全です(ログイン画面にもその旨を表示しています)。
- この自動リンクは Supabase の既定の動作で、ダッシュボードから切り替える設定項目は用意されていません。「同じ人が同じデータを見られる」ほうが自然なので、そのままで問題ありません。

### 新規ユーザーが初めてログインしたときに用意されるもの

- **種目マスタ**: ユーザーごとのデータです。サインアップ時に代表的な 15 種目がデータベースのトリガー(`seed_default_exercises`)で自動登録されます。万一登録に失敗しても**ログイン自体は必ず成功する**ようにしてあり(`supabase/migrations/20260902140000_phase7_google_login_and_new_user_seed.sql`)、その場合は「種目」タブの「代表的な種目をまとめて登録」ボタンで復旧できます。
- **食品マスタ**: 全ユーザー共通のデータです(`food_items` の `user_id` が空の行)。誰でも最初から検索・利用できます。
- **ルーティン / 目標 / からだの記録**: 最初は 0 件です。各画面に「まだ登録されていません」という案内が出るので、そこから登録してもらってください。

> このトリガーの安全化は `supabase/migrations/` のマイグレーションで行っています。**main ブランチにプッシュすると GitHub Actions が自動で本番に適用します**(→ [DB マイグレーションの運用](#db-マイグレーションの運用))。人に使ってもらう前に、Actions タブでこのワークフローが成功していることを確認してください。

## DB マイグレーションの運用

**main ブランチにプッシュすれば、アプリのコード(Vercel)もデータベースのスキーマ(Supabase)も自動で本番に反映されます。** SQL を SQL Editor にコピペする作業はもう必要ありません。

### 仕組み

- スキーマ定義は [`supabase/migrations/`](./supabase/migrations) に、Supabase CLI の命名規則(`<タイムスタンプ>_<名前>.sql`)のマイグレーションファイルとして置いてあります
- `supabase/**` に変更があるコミットが main にプッシュされると、[`.github/workflows/supabase-migrations.yml`](./.github/workflows/supabase-migrations.yml) が動き、`supabase db push` で**まだ適用されていないマイグレーションだけ**を本番に流します
- 適用済みかどうかは Supabase 側の履歴テーブル(`supabase_migrations.schema_migrations`)で管理されるので、同じファイルが二重に実行されることはありません
- GitHub Actions の **Actions** タブから手動実行(**Run workflow**)することもできます
- このワークフローは Vercel のデプロイとは独立しています。**ここが失敗しても Vercel のデプロイは止まりません**(逆も同じです)

### 今後スキーマを変更したいとき(ユーザー側の作業は不要)

1. `supabase/migrations/` に新しいファイルを追加します。ファイル名は**必ず既存より新しいタイムスタンプ**にしてください(例: `20261001120000_add_something.sql`)。`npx supabase migration new add_something` を使うと自動で採番されます
2. main にプッシュします

これだけで本番に適用されます。**シークレットを一度登録したあとは、スキーマ変更のたびにユーザーが行う作業はありません。**

> マイグレーションは**追加・変更のみ**で書いてください。`DROP TABLE` / `TRUNCATE` / データを失う型変更は本番の実データを壊します。`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` / `DROP POLICY IF EXISTS` → `CREATE POLICY` のように、何度実行しても同じ結果になる(冪等な)書き方を守ってください。

### 初回セットアップ(1 回だけ必要な作業)

自動適用を有効にするために、GitHub にシークレットを 3 つ登録します。

#### 手順 1: Supabase のアクセストークンを発行する

1. <https://supabase.com/dashboard/account/tokens> を開きます(Supabase にログインした状態で)
2. **Generate new token** をクリックし、名前に `github-actions` などを入力して発行します
3. 表示された `sbp_` で始まる文字列をコピーします。**この画面を閉じると二度と表示されません**

#### 手順 2: データベースのパスワードを確認する

1. Supabase ダッシュボードで対象プロジェクトを開きます
2. 左メニュー下部の **Settings**(⚙️)→ **Database** を開きます
3. **Database password** の欄でパスワードを確認します。分からなくなっている場合は **Reset database password** で再設定してコピーしてください

> パスワードを再設定しても、`NEXT_PUBLIC_SUPABASE_ANON_KEY` を使うアプリ本体の動作には影響しません。

#### 手順 3: プロジェクトの ref を確認する

Supabase ダッシュボードでプロジェクトを開いたときの URL

```
https://supabase.com/dashboard/project/abcdefghijklmnopqrst
                                       ^^^^^^^^^^^^^^^^^^^^ これが ref(小文字 20 文字)
```

の `project/` の後ろ 20 文字が ref です(**Settings → General** の **Project ID** でも確認できます)。`.env.local` の `NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co` の `<ref>` の部分と同じものです。

#### 手順 4: GitHub にシークレットを登録する

1. GitHub でこのリポジトリを開きます
2. 上部タブの **Settings**(リポジトリの設定。アカウントの設定ではありません)をクリックします
3. 左メニューの **Secrets and variables** → **Actions** を開きます
4. **New repository secret**(緑のボタン)をクリックし、次の 3 つを 1 つずつ登録します

| Name(名前) | Secret(値) |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | 手順 1 でコピーした `sbp_...` |
| `SUPABASE_DB_PASSWORD` | 手順 2 のデータベースパスワード |
| `SUPABASE_PROJECT_REF` | 手順 3 の 20 文字の ref |

名前は**大文字・アンダースコアまで完全に一致**させてください。登録すると **Repository secrets** の一覧に 3 つ並びます(値は伏字で表示されます)。

#### 手順 5: ワークフローを手動実行して Phase 5 を適用する

1. GitHub でこのリポジトリの **Actions** タブを開きます
2. 左の一覧から **Supabase migrations** をクリックします
3. 右側の **Run workflow** ボタン → ブランチが `main` になっていることを確認して、もう一度 **Run workflow** をクリックします
4. 数十秒待つと実行が始まります。実行をクリックすると進捗が見られます

初回の実行では、次のことが自動で行われます。

- 本番に手作業で適用済みの **Phase 1〜4 を「適用済み」として履歴に登録**します(`supabase migration repair`。既存のテーブルを作り直そうとしてエラーになるのを防ぐためです)
- **まだ適用されていない Phase 5 のマイグレーションだけ**を本番に流します

緑のチェックが付けば完了です。実行結果のページ下部のサマリーに、適用済みマイグレーションの一覧が表示されます。

> **シークレットを登録する前**にワークフローが動いた場合は、`必要なシークレットが設定されていません` という日本語のメッセージとともに失敗します(何も本番には流れません)。手順 4 を済ませてから手順 5 を実行してください。

### 注意

> ⚠️ **自動適用は「書いた SQL がそのまま本番で実行される」ということです。** 誤った SQL をプッシュすると、そのまま本番のデータベースに適用されます。テーブルやカラムを削除する変更、既存データを書き換える `UPDATE` / `DELETE` を含む変更は、プッシュ前に必ず内容を読み返してください。心配なときは、ローカルや検証用の Supabase プロジェクトで `npx supabase db push` を試してから main にプッシュすることをおすすめします。

### 旧 SQL ファイルについて

## 使い方のヒント

- **記録タブ**: 日付を選んで種目を選び、セットごとに重量と回数を入力して「追加する」。「＋ セットを追加」で何セットでも足せます。記録は後から編集・削除でき、⠿ を長押しドラッグすると種目の順番を入れ替えられます。複数の種目をまとめて消したいときは「選択して削除」から、間違ったルーティンを展開してしまったときは「この日の種目をすべて削除」から消せます(どちらも確認ダイアログのあと、数秒間は「元に戻す」で戻せます)。同じ種目の前回の記録があると、最大重量と総ボリュームの伸び(青 ↑)/落ち(赤 ↓)が記録の下に表示されます。
- **カレンダータブ**: 月表示でトレーニングした日(青)と食事記録がある日(オレンジ)を確認できます。‹ › で月を切り替え、日付をタップするとその日の内容が出て、そこから記録ページ・食事ページへ移動できます。右上の「リストで見る」で従来の履歴一覧も開けます。
- **ルーティンタブ**: 「胸の日」などの名前でルーティンを作り、種目とデフォルトの重量・回数・セットを登録。数値は「編集」からあとで変更でき、⠿ を長押しドラッグすると順番を入れ替えられます。記録タブの「ルーティンから一括追加」で、その日の記録にセットごと一括展開できます。
- **種目タブ**: 種目の追加・名前変更・削除ができます。種目が 0 件の場合は「代表的な種目をまとめて登録」ボタンで初期セットを登録できます。
- **食事タブ**: タイミング(朝/昼/夜/間食)を選び、「食品から」で検索してグラム数を入れると PFC・カロリーが自動計算されます。「写真から」で食事写真を選ぶと AI が品目を推定、「外食検索」で店名+メニュー名から栄養情報を検索できます。いずれも記録前に内容を修正できます。
- **からだタブ**: 日付と体重を入れて「記録する」。InBody を測れた日は「InBody の項目(任意)」を開いて、測れた項目だけ入力してください(体重だけの記録でも OK です)。記録は 1 日 1 件で、同じ日付で保存すると上書きされます。グラフの期間は 1ヶ月/3ヶ月/全期間で切り替えられます。
- **目標と分析**: 「からだ」タブ右上の「🎯 目標と分析」から開きます。目標体重・目標体脂肪率・達成希望日・モードを設定すると、必要なカロリー収支や達成予測日が計算されます。体重・食事の記録が増えるほど分析の精度が上がります。「アドバイスをもらう」で AI からの具体的なアドバイスを受け取れます。

## 開発コマンド

```bash
npm run dev    # 開発サーバー起動
npm run build  # 本番ビルド
npm run start  # 本番ビルドの起動
npm run lint   # Lint
```
